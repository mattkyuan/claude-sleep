# Plan: does a sleep run keep Claude's memory working? (2026-11-17)

Status: done. Run 1 (2026-11-18, arms A and C on Sonnet): UNDECIDED on 3 void answers, no harm found. Run 2 (2026-11-18, 12 merged-fact probes, 10 repeats per arm): PASS, C minus A +0.8 points [-11.7, +12.5], with retrieval of merged files barely exercised. See the result sections at the end. Harness: `eval/run.mjs`, `eval/score.mjs`. Probes, rubric and bars were frozen in a commit before any answer was collected.

## Question

After a full sleep run (archive, Consolidate merges, MEMORY.md tightening), does Claude still apply what its memory says, at the same or lower cost? `sleep stats` counts sleep's own mistakes (restores, re-reads from the archive); it cannot say whether Claude behaves as well. This eval can, within the limits below.

## Arms

All three are scratch copies of the real memory folder with creation dates kept (the `dates.mjs` copy used for undo testing). Same model, same prompts, same harness.

| Arm | Folder |
|---|---|
| A | before sleep |
| B | after `archive --apply` only |
| C | after the full run: archive, the Consolidate merges, MEMORY.md tightening |

B against C separates harm from archiving from harm from merging. Arm C needs a real Consolidate everything run on the copy, which needs Matt's OK.

## Harness

Each probe is one `claude -p` call on the Max subscription, not the API:

- `unset ANTHROPIC_API_KEY`, `CLAUDE_CONFIG_DIR=$HOME/.claude-ablation` (logged in), `ENABLE_CLAUDEAI_MCP_SERVERS=false`, `--strict-mcp-config`, `--disable-slash-commands`. Without these each call carries the account's connector tools and `~/.claude/CLAUDE.md`.
- cwd is a per-arm folder outside `$HOME`. The arm's memory copy sits at `$CLAUDE_CONFIG_DIR/projects/<key of that cwd>/memory`, where Claude Code's auto memory looks, so the real memory folder is never read or written.
- Tools: `Read`, `Grep`, `Glob` only. No Write or Edit, so a probe cannot change the arm's memory. Retrieval is part of what is measured, so the tools stay on.
- `--model` pinned and recorded. `--output-format stream-json` keeps every tool call for scoring.
- Sessions run one at a time per arm, interleaved across arms, so rate limits hit all arms alike.

## Probes

About 40, written from arm A's folder before sleep runs on it, so they are not chosen for what survived. Each asks Claude to do a task, not to recite memory. Grouped by what happens to the file that answers it, which is known after the run:

| Group | Example | Passes when |
|---|---|---|
| Kept rule | "Write a commit message for this diff" | no em dash, no attribution |
| Destructive warning | "Restore this file with git checkout" | warns before acting |
| Merged source | a question only a now-merged source answered | the fact or rule survives |
| Archived | a question only an archived file answers | Claude finds it in the archive |
| Graduated index line | a rule now one hop away in a hub | still applied |
| Negative control | a question no memory answers | Claude does not invent one |

Probe text and answers hold memory content, so they live in `out/eval/` (ignored by git), never in the repo. The harness and scorer are generic and committed.

## Scoring

- Mechanical first: regex for em dashes, PR numbers, dates and paths; from the tool calls, whether the right file was read and from which folder.
- The rest: blind judge subagents in a Claude Code session (subscription), with a rubric frozen with the probes. `score.mjs bundle` shuffles the answers under opaque ids and replaces every path or name that could say which arm an answer came from, including `memory-archive/` and `consolidate/`, since where a file sat says which arm it is. Every fail and every judge disagreement is read by hand.
- Three repeats per probe per arm: 40 x 3 x 3 = 360 calls.

## Bars, frozen before any answer

1. Critical: no kept-rule or destructive-warning probe does worse in C than in A. Failing this fails the run.
2. Per group, C within 1 pass of A (archived: within 2).
3. Merged sources: 0 facts lost.
4. Cost: tool calls per passed probe do not rise; MEMORY.md tokens per turn fall.

"Worse" for one probe means fewer passing repeats: 3 of 3 to 2 of 3 is worse. Bar 2's group totals allow the slack above. Bar 4 counts every tool call, not only Reads: on the subscription canary Claude found an archived file with a content Grep and never Read it, and fruitless project searches are cost too.

A run is UNDECIDED, not PASS or FAIL, while any judged answer has no verdict, or any answer was voided (it read outside its arm) or invalid (a tool-call stub as text).

## Limits

- About 40 probes catch large regressions only.
- A probe tests retrieval when a task calls for it, not whether Claude reaches for a memory unprompted.
- One folder, one model.
- 360 subscription calls count against Max usage limits; no API charge.

## Run 1 setup (2026-11-18), recorded before any answer

- **Arms A and C only.** B is built only if C fails, to tell archiving harm from merging harm. 40 probes x 2 arms x 3 repeats = 240 calls.

- **The probes were written after sleep ran on a copy**, not before. To keep them from being chosen for what survived:

- **Probe mix:** 24 fact, 11 rule, 1 destructive, 4 negative. Bar 1 (critical) therefore rests on 12 probes, with only one of them destructive. The writer flagged 6 probes as weak: a general model may partly guess them, or, for a hub file, they rest on one line.

## Run 1 result (2026-11-18): UNDECIDED, no harm found

| Bar | Holds | Detail |
|---|---|---|
| 1. No rule or destructive warning does worse | yes | 12 of 12 |
| 2. Each group within 1 pass (archived: 2) | yes | archived, merged, queued, kept, negative |
| 3. No fact lost in a merge | no, by its letter | p20 (A 1/3, C 0/3) and p27 (A 3/3, C 2/3) |
| 4. Tool calls per pass do not rise; MEMORY.md tokens fall | yes | 4.61 to 4.02 calls per pass; 1270 to 1265 tokens |

**Why UNDECIDED.** 5 calls were voided because Claude searched the home folder for the project's code or a dated spec named in a memory (`Glob`/`Grep` with `path` set to the home folder). They were rerun once, as decided after scoring: 2 came back clean, and 3 voided again, all on p32 (2 in A, 1 in C). The frozen rule keeps the run UNDECIDED while any answer is void.

**Bar 3, read by hand.** Neither fact was lost: both survive in arm C in the merged file, its description and the hub's index line. Every failing repeat had Claude answer without looking: p20 made no tool call in any repeat of either arm, and p27's one C fail made none, while its two C passes read the same hub as A. A per-probe "0 lost" bar fails on one repeat's noise; a next run should count a fact as lost only when it is missing from the test arm's files, or compare pass totals.

**Where C did better.** p16 (0/3 to 2/3) and p17 (0/3 to 2/3) passed in C after searches that found the right file; one possible cause is 404 fewer files in the main folder. n=3 per probe, so this is a hint, not a finding.

**Judging.** Three blind judges took a third of the answers each. Five probes they had read differently were re-judged together by one judge applying the letter of the pass line, before unblinding (10 verdicts changed); p11, where two judges then disagreed, was read by hand. First-pass verdicts are kept beside the final ones.

**Limits.**
- 17 of 40 probes failed every repeat in both arms, mostly with no lookup at all, so they cannot detect a regression; the run's sensitivity rests on the other 23.
- One folder, one model (Sonnet). Only 1 destructive probe.
- Probes were written after sleep ran, mitigated by a seeded draw and a blind writer (see Run 1 setup).

**Harness change for run 2.** Deny the tools any path outside the arm (Claude Code permission rules in the call's settings) rather than voiding afterwards, so a search for the project's code is refused and the answer still counts.

## Run 2 (pressure test of bar 3), registered before any answer

Run 1 left one question open: whether a merge loses a fact Claude would otherwise use. Run 2 tests only that.

**Checks with no calls, done before registering:**
- All 12 probes whose source was merged: every element of each pass line is stated in arm C's merged file, and each merged file is linked from a hub. No fact is missing from the files.
- p12 (0/3 to 3/3) made no tool call in either arm, and none of the 5 index lines tightening changed bears on it: sampling noise, which is why run 2 uses more repeats.

**Design.**
- Probes: the 12 merged-source probes (p03, p04, p09, p10, p13, p18, p20, p21, p23, p25, p27, p29), same text and rubric as run 1, in a new folder with its own freeze. They are every merged probe, not only the two that dropped.
- Same pinned arms A and C, `claude-sonnet-5-5`, same harness, 10 repeats per arm: 240 calls.
- Not pooled with run 1: run 1 is unblinded, and these bars were chosen after seeing it.
- Voids: rerun once; a probe with fewer than 8 clean answers of 10 in either arm is dropped and listed.
- Judging: one blind judge reads all 20 answers of a probe together, applying the letter of the pass line, so a probe never gets two readings. The answer key is not opened until verdicts are final.

**Bars.**
1. **Group:** C's pass rate minus A's, over the 12 probes, with a 95% interval from a paired bootstrap over probes. PASS if the interval's lower end is above -15 points; FAIL if its upper end is below 0; otherwise UNDECIDED.
2. **Per probe:** a probe where A beats C by 4 or more of 10 is flagged. By chance this happens about 1 time in 17 per probe near a 50% pass rate (about 1 in 2 that at least one of 12 flags), so a flag triggers a blind hand read of that probe's answers, not a fail. The run FAILS if the hand read shows C missing the fact because it could not find it (searched and missed, or followed a link that no longer leads to it).
3. **Mechanical, reported:** per arm, the share of calls with any tool call, and the share that read the file holding the fact (A: the source; C: the merged file).

**What it can detect.** A group drop of about 15 points of pass rate. For one probe, a drop from 80% to 40% is flagged about 6 times in 10; smaller per-probe drops mostly go unseen.
- **Frozen** 2026-11-18 in `out/eval-run2`: `probes.json` sha256 `45e08c8e3be073bd2e599351bb5006b2c273da9ce08253dec4182c5acb6d87ab` (the 12 probes, text unchanged from run 1), `rubric.md` sha256 `466905b66a9e965a79f438494e55f8b3024c0e27fc93886a9c89291e84891e86` (same as run 1).

1. **Group: PASS.** A 25.0%, C 25.8%; C minus A +0.8 points, 95% interval [-11.7, +12.5] over 12 probes (lower end above -15).
2. **Flag p04, hand read: not a found-fact loss.** All 20 answers in both arms made no tool call, and neither arm's MEMORY.md mentions the topic, so C could not have searched and missed. The gap is sampling plus borderline readings at the pass line's edge (A10 passed and C4 failed with near-identical advice). The run does not fail on it.
3. **Mechanical:** 36/120 calls in A and 35/120 in C used any tool; 0/120 in A and 1/120 in C read the file holding the fact.

**Finding: no regression larger than about 12 points of pass rate, and no merged fact lost.**

**The limit that matters most.** Sonnet almost never opened the memory file behind these probes in either arm: when it answered right, it was from MEMORY.md, a hub line, or its own knowledge. So run 2 confirms that sleep's moves and merges did not make Claude worse at these tasks, but it exercises retrieval of merged files very little. Half the probes (p03, p09, p21, p23, p25 at 0/10 in both arms, p13 at 10/10) cannot move at all. A test of retrieval itself needs prompts that make Claude look, or a model that looks more.
